# Render deployment (superseded)

> The Vite/Express/Drizzle deployment described below is legacy audit material. The production service is now `atlas-web`, built by the repository root `Dockerfile` and configured in `render.yaml`. See `ATLAS_MIGRATION.md` and `atlas-web/README.md` for the authoritative runbook.

## Recommended service

This repository is packaged as a single Docker web service. Create a Render Blueprint from `render.yaml`, or create a Web Service manually with **Runtime: Docker** and the included `Dockerfile`. The service listens on Render's injected `PORT`, serves the compiled SPA, and exposes the tRPC API under `/api/trpc`.

## Database compatibility

The current application uses Drizzle with `mysql2` and MySQL/TiDB SQL migrations. `DATABASE_URL` must therefore point to a reachable MySQL-compatible database. Render's native PostgreSQL database is not drop-in compatible with the current schema; using Render Postgres would require a deliberate migration to `drizzle-orm/node-postgres`, PostgreSQL table definitions, and new migrations. The Render Blueprint leaves `DATABASE_URL` as a secret value for the MySQL/TiDB provider you choose.

## Required configuration

The Blueprint declares the server-side secret slots. After creating the service, fill in `DATABASE_URL`, `VITE_APP_ID`, `VITE_OAUTH_PORTAL_URL`, `OWNER_OPEN_ID`, `BUILT_IN_FORGE_API_URL`, `BUILT_IN_FORGE_API_KEY`, and `GROQ_API_KEY` if the live model path is enabled. `JWT_SECRET` is generated by Render. Configure `ATLAS_SERPAPI_API_KEY` and set `ATLAS_ENABLE_SERPAPI=true` only when live research is desired. Cloudinary variables are available for the wardrobe storage path; Telegram delivery remains disabled by default.

Never commit secret values or expose server-only keys through `VITE_*` variables. Add the Render service URL to the OAuth provider's allowed origins and callback configuration when authentication is enabled.

## Deploy steps

1. Push the project to a Git provider and select **New → Blueprint** in Render.
2. Select the repository and let Render detect `render.yaml`.
3. Fill the `sync: false` variables in the Render dashboard. Keep Telegram delivery disabled until its consent and delivery workflow is intentionally reviewed.
4. Deploy and wait for the Docker build to finish. The container runs `pnpm check` and `pnpm build` during image creation.
5. Open the generated Render URL. The health check is `/`; the web UI and `/api/trpc` are served by the same process.
6. Run the release checks locally before future deploys:

```bash
pnpm install --frozen-lockfile
pnpm check
pnpm test
pnpm build
```

## Database migrations

Apply Drizzle migrations in order to the production MySQL/TiDB database using the approved migration process. The current feature set includes `atlas_try_ons`, `atlas_looks`, and `atlas_travel_plans`. Back up the production database before applying a new migration.

## Production behavior

The web process is stateless between requests. Persistent records live in the database and uploaded/generated image references live in configured storage. If the model or research connector is unavailable, the application returns bounded safe fallbacks and labels them rather than presenting them as verified evidence. Render logs should be monitored after the first deploy for database connectivity, OAuth callback errors, and provider rate limits.
